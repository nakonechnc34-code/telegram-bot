# Бесплатное резервное копирование Supabase PostgreSQL в Cloudflare R2

## Что это

Веб-приложение работает в Amvera, база PostgreSQL находится в Supabase Free. На бесплатном плане Supabase нет встроенных scheduled backups. Workflow `.github/workflows/database-backup.yml` запускается в 02:15 UTC ежедневно после слияния в `main` и может запускаться вручную. Он сохраняет зашифрованный дамп в **приватный** Cloudflare R2 bucket. Ни дамп, ни приватный ключ расшифровки не публикуются в GitHub.

**Не считайте защиту данных завершённой до первого успешного backup и проверенного восстановления.** Бесплатные квоты, условия биллинга и доступность R2 нужно проверить в своём аккаунте. Для R2 может потребоваться платёжный метод.

## Настройка Cloudflare R2

1. Создайте аккаунт Cloudflare, активируйте R2, проверьте условия и квоты.
2. Создайте **приватный** bucket (например, `wokker-db-backups`); не включайте public access, публичный домен и публичные ссылки.
3. Создайте R2 API token с правами чтения и записи **только этого bucket**. Храните Access Key ID и Secret Access Key отдельно от кода.
4. В bucket настройте lifecycle для префикса `postgres/daily/`, например удаление объектов старше 14 дней. Это начальный срок, который следует согласовать с требованиями хранения и восстановления. Lifecycle управляется в Cloudflare, не GitHub.
5. Защитите доступ к аккаунту Cloudflare с помощью MFA. Доступ к резервным копиям должен быть только у ответственных администраторов.

## Ключ шифрования

На доверенном компьютере установите `age` и выполните:

```bash
age-keygen -o wokker-backup-identity.txt
```

**Приватный ключ** в файле `wokker-backup-identity.txt` храните в защищённом офлайн-хранилище, отдельно от GitHub, Cloudflare и Amvera. Потеря ключа делает резервные копии невосстановимыми. Создайте защищённую резервную копию ключа. **Никогда не отправляйте его в чат.**

Публичный recipient вида `age1...` указан в выводе команды (или `age-keygen -y wokker-backup-identity.txt`). Его можно использовать в настройках GitHub.

## Настройка GitHub

После проверки и объединения PR откройте Repository → Settings → Environments и создайте environment `production-backup`. В нём задайте:

**Environment secrets** (значения скрыты):
- `BACKUP_DATABASE_URL`: отдельная строка подключения Supabase PostgreSQL, желательно отдельная read-only учётная запись с доступом ко всем нужным таблицам и схемам. Добавьте `sslmode=require` (или `sslmode=verify-full` с корректными сертификатами). Используйте **Direct connection или Session pooler**, не transaction pooler. Убедитесь, что GitHub-hosted runner может достучаться до адреса: direct может требовать IPv6; session pooler обычно подходит при IPv4. Не копируйте пароль в логи или чат.
- `R2_ACCESS_KEY_ID`: Access Key ID ограниченного R2 API token.
- `R2_SECRET_ACCESS_KEY`: Secret Access Key того же токена.

**Environment variables** (не секреты):
- `R2_ACCOUNT_ID`: идентификатор аккаунта Cloudflare R2.
- `R2_BUCKET`: имя приватного bucket.
- `BACKUP_AGE_RECIPIENT`: **публичный** ключ age вида `age1...`.

Проверьте, что все шесть значений заданы. Workflow не начнёт backup, если чего-то не хватает.

**Важно:** по умолчанию environment в GitHub не обеспечивает обязательного ручного подтверждения. Настройте доступ к изменению workflow и secrets, защиту `main`, MFA и минимальные разрешения. Не храните реальную строку подключения в `.env.example`, коде или PR.

## Проверка работы

1. После объединения workflow появится на `main` в Actions → Encrypted PostgreSQL backup. Запустите `Run workflow` вручную.
2. Убедитесь, что запуск успешен, а в R2 появился объект `postgres/daily/*.dump.age`.
3. На доверенном компьютере скачайте объект из R2 и расшифруйте локально:

```bash
age -d -i wokker-backup-identity.txt -o backup.dump postgres-backup.dump.age
pg_restore --list backup.dump
```

4. Восстановите в **отдельную пустую тестовую PostgreSQL** с помощью `scripts/verify_restore_postgres.sh`, не в production. Проверьте таблицы и несколько ключевых сценариев веб-приложения. Удалите локальные незашифрованные дампы безопасным способом в соответствии с вашей политикой хранения.

## Ограничения и дальнейшие меры

- Это логические дампы PostgreSQL, а не point-in-time recovery. Максимальная потеря данных при ежедневном расписании может достигать суток и больше при пропущенном запуске.
- GitHub schedule может запускаться с задержкой; проверяйте историю запусков и настройте уведомления об ошибках.
- Скрипт проверяет размер загруженного объекта, но не скачивает и не расшифровывает его. Периодически проверяйте восстановление вручную.
- В дамп не включаются файлы из Supabase Storage, Amvera uploads и другие внешние сервисы; для них нужны отдельные backup-процедуры.
- Версия `pg_dump` должна быть не старее major-версии сервера PostgreSQL. При ошибке несовместимости обновите PostgreSQL client в workflow.
- Данные сотрудников могут подпадать под требования законодательства о персональных данных, включая требования к местонахождению и трансграничной передаче. **До переноса копий в Cloudflare R2 согласуйте допустимость выбранного региона и провайдера** с ответственным за защиту персональных данных. При невозможности соблюсти требования используйте согласованное хранилище вместо R2.
