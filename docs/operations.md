# Эксплуатация веб-системы Wokker

Проект является веб-приложением. Интеграция с Telegram планируется отдельно.

## Проверки перед публикацией

Workflow `.github/workflows/quality.yml` запускается при Pull Request и push в `main`: Python 3.11, компиляция модулей, pytest, проверка синтаксиса shell-скриптов и отдельный аудит зависимостей через pip-audit. Ошибка любого задания означает, что выпуск следует остановить до разбора причины. В GitHub рекомендуется настроить branch protection и обязательные checks; эти настройки не применяются автоматически.

Зависимости сейчас заданы диапазонами. Для воспроизводимых релизов следующим шагом следует закрепить версии с помощью lock-файла и автоматического обновления зависимостей.

## Резервные копии PostgreSQL

**Важно:** медицинские данные и сведения о сотрудниках являются конфиденциальными. Не помещайте дампы в репозиторий, каталог uploads, публичный веб-каталог или артефакты GitHub Actions.

Для создания резервной копии необходимы клиентские утилиты PostgreSQL (pg_dump и pg_restore), доступ к базе и защищённый каталог:

```bash
export DATABASE_URL='postgresql://...'
export BACKUP_DIR='/secure/backups/wokker'
bash scripts/backup_postgres.sh
```

Скрипт создаёт дамп в формате PostgreSQL custom, проверяет читаемость оглавления, записывает файл с приватными правами и публикует его атомарно. **Проверка оглавления не гарантирует успешное восстановление.** После создания необходимо перенести копию в отдельное зашифрованное хранилище с ограничением доступа, настроить ротацию и уведомления об ошибках. Рекомендуемый начальный регламент: ежедневно, хранить 7 ежедневных и 4 еженедельных копии; адаптировать под требования бизнеса и законодательства. Планировщик и внешнее хранилище в этом PR не подключаются, так как для этого нужны инфраструктура и секреты.

## Проверка восстановления

Создайте **новую пустую тестовую базу** отдельно от production и используйте её URL:

```bash
export RESTORE_DATABASE_URL='postgresql://.../wokker_restore_test'
CONFIRM_DISPOSABLE_RESTORE=YES bash scripts/verify_restore_postgres.sh /secure/backups/wokker/backup.dump
```

Скрипт откажется работать без явного подтверждения или если в целевой базе есть пользовательские таблицы. **Не указывайте рабочую базу даже для теста.** После восстановления проверьте данные и основные сценарии приложения в изолированном окружении. Не используйте тестовую копию для реальных уведомлений или рассылок.

## Контроль выпуска

1. Проверить зелёные GitHub Actions и изменения в Pull Request.
2. Убедиться, что последняя резервная копия существует во внешнем хранилище и её восстановление проверено.
3. Развернуть новую версию в тестовом окружении, проверить вход, табель, медкнижки и Академию.
4. Развернуть production, проверить `/api/health` и ошибки приложения.
5. При проблемах откатить версию приложения; откат базы выполнять только по отдельному плану восстановления.

Выполнение тестов в CI не заменяет интеграционные тесты с реальной PostgreSQL и мониторинг продакшена.
