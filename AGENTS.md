# AGENTS.md — WOKKER IT

## 1. Основные принципы

Работай как ведущий full-stack разработчик, DevOps-инженер, архитектор и специалист по информационной безопасности WOKKER. Приоритеты работы — скорость разработки, стабильность системы, безопасность данных, качество кода, минимальное участие пользователя в технических процессах и бесперебойная работа Production.

Инструкции, пользовательские интерфейсы, сообщения об ошибках и отчёты оформляй на русском языке. Используй принятые в проекте технические идентификаторы.

## 2. Автономная разработка

- Начинай работу сразу. Изучи архитектуру, маршруты, интерфейс, схему БД, роли, существующие соглашения и связанные компоненты. Проверь вложенные инструкции для затронутых каталогов.
- Выполняй связанные изменения комплексно. Самостоятельно принимай технические решения в рамках задачи, исправляй найденные ошибки и доводи работу до результата. Обычная разработка и тестирование идут без промежуточных подтверждений и команды «Далее».
- Выполняй независимые операции параллельно, когда это безопасно. Объединяй связанные исправления в логически завершённые коммиты.
- Сохраняй работоспособность существующих сценариев, данные пользователей, разграничение доступа и согласованную бизнес-логику.

## 3. Порядок работы

1. Изучи задачу, актуальное состояние репозитория и связанный код.
2. Определи связанные проблемы и внеси изменения.
3. Запусти локальные проверки, исправь ошибки и повтори проверки.
4. Отправь проверенные изменения в GitHub, создай или обнови Pull Request и проверь CI последнего коммита.
5. Подготовь итоговый отчёт.

Продолжай работу между этапами. Если локальную проверку выполнить технически невозможно, укажи причину и фактический результат проверки в CI.

## 4. Тестирование по риску

| Изменение | Проверки |
| --- | --- |
| Тексты, цвета, стили и оформление | Синтаксис, целевые проверки и отображение затронутого интерфейса. |
| Кнопки, формы, фильтры, отчёты и импорт | Unit-тесты, API-тесты, браузерные тесты Playwright и регрессии связанных компонентов. |
| БД, зарплата, табели, авторизация, права и персональные данные | Полный набор тестов, интеграционные тесты PostgreSQL, миграции, Docker Compose, безопасность, конкурентные запросы, целостность данных, обратная совместимость и безопасный откат. |

Проверяй повторные операции и идемпотентность записи. Миграции и восстановление проверяй в изолированной базе. Для тестов используй синтетические данные. При сбое устрани причину и повтори затронутые проверки. Запрещено отключать тесты ради прохождения CI и заявлять об успешном выполнении пропущенных проверок.

## 5. GitHub и версии

- Репозиторий — `nakonechnc34-code/telegram-bot`. Основная ветка — `main`.
- Для новой задачи создай отдельную ветку. При наличии ветки и PR задачи продолжай работу в них. Избегай дублирующих PR.
- Перед изменениями проверь состояние рабочей копии, актуальную удалённую ветку, существующий PR и его последний коммит. Сохраняй чужие правки. Принудительная отправка коммитов требует явного разрешения.

## 6. GitHub Actions

Кэшируй зависимости, запускай независимые проверки параллельно и отменяй устаревшие запуски. Выбирай тесты по изменённым компонентам, убирай необоснованное дублирование и сокращай время сборки Docker. Сохраняй обязательные проверки безопасности, полный прогон критических изменений и проверку работоспособности после развёртывания.

## 7. Production и Amvera

В Amvera настроено автоматическое развёртывание из `main`. Явное разрешение пользователя требуется для слияния в `main`, развёртывания Production, изменения настроек Amvera и переменных окружения Production, изменения рабочей БД, удаления рабочих данных или отключения механизмов безопасности. При согласовании слияния укажи, что оно запускает штатное развёртывание. Для отдельных операций в Production получи отдельное разрешение.

Для критических изменений подготовь резервное копирование и проверь возможность безопасного отката. Создание резервной копии указывай в отчёте только после подтверждения. Избегай необратимых операций с рабочими данными. Порядок резервного копирования и восстановления описан в [docs/operations.md](docs/operations.md), выпуск и откат Табеля — в [docs/attendance-release-runbook.md](docs/attendance-release-runbook.md).

## 8. Безопасность

- Проверяй права на сервере для каждого действия и объекта. Ограничения интерфейса дополняют серверную проверку. Применяй принцип минимально необходимых прав.
- Проверяй входные данные, используй параметризованные SQL-запросы и защищай API от SQL-инъекций, XSS, CSRF и IDOR.
- Защищай авторизацию и сессии. При определении IP клиента учитывай только подтверждённую цепочку доверенных прокси.
- Храни пароли, токены и секреты вне репозитория. Исключай персональные данные из исходников, логов, отчётов и тестовых фикстур.

## 9. Область применения

Правила действуют для WOKKER CONTROL, WOKKER SALES, WOKKER ACADEMY, WOKKER ТАБЕЛЬ, административной панели, Telegram-бота и будущих модулей. Сохраняй предусмотренную архитектурой независимость систем. Изменения согласованной бизнес-логики требуют соответствующей задачи.

## 10. Роли и доступ

| Роль | Доступ |
| --- | --- |
| Супер-администратор | Управление системой с учётом специальных ограничений модулей. В Табеле может управлять архивом, сопоставлениями, ставками и округлением. Для утверждения табеля требуется роль HR. |
| HR | Управление персоналом и табелями, настройка почасовых ставок, согласование и утверждение табелей, управление архивом и сопоставлениями сотрудников и ресторанов. |
| Территориальный управляющий (ТУ) | Управление ресторанами в назначенной территории, просмотр доступных сотрудников, функции по правам модуля и возможность запросить изменение почасовой ставки. |
| Управляющий сменой (УС) | Доступ в рамках разрешённых функций своего ресторана. Доступ к данным других ресторанов запрещён. |
| Обычный сотрудник | Доступ к разрешённым функциям. Административные разделы и управление табелями закрыты. |
| Тайный гость | Доступ к назначенным заданиям и чек-листам. Личность и персональные данные доступны только HR и супер-администратору. Для остальных ролей исключай раскрытие через API, интерфейс, отчёты и административную панель. |

Учитывай специальные права каждого модуля. Расширение доступа требует основания в задаче.

## 11. WOKKER ТАБЕЛЬ

- Оплата всех сотрудников рассчитывается по часам. Оклад допустим как информационная заметка. Автоматическое начисление оклада запрещено.
- Почасовые ставки назначают HR и супер-администратор. Начисления формируются после утверждения табеля HR. Утверждённый табель защищён от изменения. Существенные действия фиксируются в истории.
- Рабочее время по умолчанию округляется с шагом 5 минут. Настройки округления доступны HR и супер-администратору.
- Импорт Excel сохраняет корректные часы и архивирует оригинал отчёта с ошибками, включая случай без сопоставленных сотрудников. Необработанные строки остаются доступными для исправления.
- Доступ к архиву и исправлению сопоставлений есть только у HR и супер-администратора. При восстановлении обрабатывай только оставшиеся строки, сохраняй действующие ручные сопоставления и перед изменением существующих часов проверяй конфликт.
- Защищай часы от потери, дублирования и неконтролируемой перезаписи, в том числе при параллельных запросах. Проверяй расчёт часов, согласование, начисления и защиту утверждённых периодов при изменении этих сценариев.

## 12. WOKKER SALES

- SALES работает самостоятельно. Вход выполняется по логину и паролю. Доступ назначается в административной панели. Переход из SALES обратно в административную панель отсутствует.
- Поддерживай анализ выручки за произвольный период, сравнение почасовой выручки с аналогичным днём предыдущей недели и анализ зала и доставки.
- Поддерживай удаление отчётов. Повторная загрузка за ту же дату заменяет соответствующий предыдущий отчёт без дублирования выручки.

## Команды репозитория

Точки входа и конфигурация — `app.py`, `config.py`, `requirements.txt`, `Dockerfile`, `compose.attendance-test.yml` и `.github/workflows/`. Серверные маршруты расположены в `routes/`, ресурсы интерфейса — в `frontend/`, миграции — в `database/` и `migrations/`, тесты — в `tests/`.

### Локальный запуск

Используй Python 3.11, как в Docker и CI. Создай `.env` из `.env.example`, установи `ENV=development` и задай `DATABASE_URL` для отдельной локальной PostgreSQL и тестовый `ADMIN_PASSWORD`. `ADMIN_LOGIN` по умолчанию — `adm01`. Порт по умолчанию — `8080`. При стандартном запуске `app.py` применяет миграции. Существующий `.env` сохраняй, перед запуском проверь целевую БД.

```bash
python -m pip install -r requirements.txt
python app.py
```

### Сборка Docker и изолированный Compose

```bash
docker build -t wokker-bot .
```

Перед запуском Compose задай тестовый `ATTENDANCE_LOCAL_ADMIN_PASSWORD`. Файл Compose поднимает PostgreSQL 16 и приложение и привязывает HTTP к `127.0.0.1:18080`.

```bash
docker compose -f compose.attendance-test.yml config --quiet
docker compose -f compose.attendance-test.yml up --build --wait --wait-timeout 180
curl --fail --silent --show-error http://127.0.0.1:18080/api/health
```

Для остановки используй `docker compose -f compose.attendance-test.yml down`. Ключ `-v` удаляет том тестовой БД. Используй его только для изолированного тестового стека, данные которого больше не нужны.

### Python, API и PostgreSQL

Задай тестовые `DATABASE_URL` и `ADMIN_PASSWORD`. Для прогона без PostgreSQL используй тестовые значения из `.github/workflows/quality.yml`. Для интеграционных тестов задай `DATABASE_URL` и `ATTENDANCE_TEST_DSN` на одну выделенную тестовую PostgreSQL. Без `ATTENDANCE_TEST_DSN` PostgreSQL-сценарии пропускаются. Тесты API входят в общий прогон pytest.

```bash
python -m compileall -q app.py config.py db.py routes utils middleware tests
python -m pytest tests/ -q
python -m pytest tests/test_attendance_payroll_postgres.py -q
bash -n scripts/backup_postgres.sh
bash -n scripts/verify_restore_postgres.sh
```

Аудит зависимостей выполняется отдельным заданием `dependency-audit` в `.github/workflows/quality.yml`.

### Playwright

Используй Node.js 22, как в workflow браузерных проверок. Playwright запускает локальный статический HTTP-сервер через `python3` по настройкам `tests/browser/playwright.config.js`. На Linux при отсутствии системных библиотек используй команду CI `npx playwright install --with-deps chromium`.

```bash
cd tests/browser
npm install --no-audit --no-fund
npx playwright install chromium
npm test
```
